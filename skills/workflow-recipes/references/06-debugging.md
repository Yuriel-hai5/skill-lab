# 06 · 排错

## 适用信号

- "报错了 / 跑不起来 / 启动失败"
- "有时好有时坏"、"间歇性失败"
- "变慢了 / 性能回退"
- "本来好好的，改完之后就不对了"
- 环境问题（装不上、找不到命令、路径不对）

## 核心原则

**在拿到一个能在这个 bug 上变红的信号之前，盯着代码看多久都没用。**
`diagnosing-bugs` 的第一阶段就是建这个 feedback loop——建对了，bug 好了 90%。

## 配方

### 1. `diagnosing-bugs`（主导）

**Phase 1 —— 建 feedback loop**（投入不成比例的精力，要强硬、有创造力、拒绝放弃）。
按这个顺序尝试：

1. **失败测试**，放在能触达 bug 的 seam 上（unit / integration / e2e 都行）
2. **curl / HTTP 脚本** 打到运行中的 dev server
3. **CLI 调用** + fixture 输入，把 stdout 与 known-good 快照 diff
4. **无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，断言 DOM / console / network
5. **重放捕获的 trace**：把真实请求 / payload / 事件日志存盘，隔离环境重放
6. **一次性 harness**：启动系统最小子集，一次函数调用触发 bug 路径
7. **property / fuzz 循环**：如果是"有时输出错"，跑 1000 个随机输入找失败模式
8. **bisection harness**：bug 出现在两个已知状态之间 → 自动化 "boot at X, check, repeat"，配合 `git bisect run`
9. **差分循环**：同一输入跑旧版本 vs 新版本（或两套配置），diff 输出
10. **HITL bash 脚本**（最后手段）：必须人工点击时，用 `scripts/hitl-loop.template.sh` 把**人**驱动起来

**然后 tighten 它**：能更快吗？信号能更尖锐吗（断言具体症状而不是"没崩"）？能更确定性吗（pin 时间、seed RNG、隔离文件系统、冻结网络）？

**之后**：minimise → hypothesise → instrument → fix → **加回归测试**

**产出**：一个能在修复前变红的测试（回归测试）+ 修复。

### 2. 根因是架构问题 → `improve-codebase-architecture`

如果复盘发现真正的问题是**没有好 seam 能锁住这个 bug**（测试无从下手、改动会波及一片），
那就不是 bug 的问题，是结构的问题。转 [07-refactoring](07-refactoring.md)。

### 3. 环境问题先查真实环境

**不要用工具进程里的环境变量当结论。** 判断环境问题前，先用 PowerShell 读注册表核对真实值：

```powershell
Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment"
Get-ItemProperty "HKCU:\Environment"
```

工具进程可能不继承真实环境（缺 `JAVA_HOME`、`APPDATA`、`TEMP`，或注入 `MSYS_NO_PATHCONV` 之类）。
**先核对，再下结论**——否则会误判"环境坏了"，其实是工具进程的假象。

### 4. 验证 —— 用用户当初报现象的方式再走一遍

**测试通过 ≠ 问题解决。** 回归测试是**必要条件，不是充分条件** ——
它证明的是"你锁住的那个点不再复现"，不等于"用户报的那个现象消失了"。

修复后按这个顺序确认：

1. **原样复现一遍** —— 按用户当初描述的操作路径走，不是你造的那条更顺手的路径。
   他说"点保存之后列表不刷新"，就点保存看列表刷不刷新，
   别用 curl 打接口说"返回 200 所以没问题"。
2. **边界也走一遍** —— 空输入、超长输入、连点两次、断网重试。当初能触发它的那些条件。
3. **确认没打坏别处** —— 跑一遍相关测试；改的是公共方法就多跑一层。
4. **能演示** —— 修之前 / 修之后各演示一次。**演示不出来 = 没修好。**

**产出**：一句明确的结论 ——「你当初报的 X，现在这样做已经不出现了」，
而不是「测试绿了」。

> 复现不出来（环境变了、数据没了）→ **直说**，别用"应该好了"糊过去。

## 需确认

- 涉及展示命令输出时**先 redact 掉所有 secret**（用 `<REDACTED>` 替换）。
  凭据留在环境变量里，不要进到展示内容里。
- 捕获的 artifact 带 auth header 时，只引用携带信号的那几行。
- 如果 redact 后信息不足以诊断，**说明情况并问用户**，不要自己脑补。

## 常见坑

1. **没有 loop 就开始读代码。** 这是本阶段最常见的浪费。
2. **loop 太松**：断言"没崩溃"而不是断言具体症状。
3. **loop 不确定**：时间、随机数、网络没冻结，跑三次三个结果。
4. **修完不加回归测试**。bug 会回来。
5. **跳过 minimisation**：在 500 行复现里找原因，而在 5 行里一眼就能看出来。
6. **拿工具进程的环境当真实环境**（见上）。

7. **测试绿了就收工，没复测原现象。** 见上面配方第 4 条 —— 回归测试是必要条件，不是充分条件。

## 边界

- 只是要理解某段代码怎么工作 → 用 `research` 或直接读代码
- 已知根因是结构问题、要系统性改进 → [07-refactoring](07-refactoring.md)
