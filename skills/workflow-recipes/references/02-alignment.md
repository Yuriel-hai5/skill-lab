# 02 · 需求对齐

## 适用信号

- "我怕做出来不是我要的"
- "你先别写代码，我们先把需求理清楚"
- 需求文档很模糊（"做个好看的后台"、"要智能一点"）
- 已经开工了但感觉方向在漂

## 为什么这一步不能省

软件开发最常见的失败模式不是写错代码，是**做错东西**。
agent 拿到模糊需求会用自己的默认理解填空白，那个理解几乎一定和你想的不一样。
对齐的代价是几轮对话；不对齐的代价是整段工作重做。

## 配方

1. **`grill-with-docs`**（主导，有 repo 时）
   - 它做的是**持续追问**：把需求映射成一棵 **design tree**，每个决策分支到它下面的决策
   - 按 **rounds** 推进：一轮问完当前 **frontier**（前置条件已敲定、现在就能答的问题），
     每个问题带推荐答案，等你回答，再算下一轮 frontier
   - **事实是它的活**（它派 sub-agent 去查文件/环境，不问你）；**决策是你的活**（逐个交给你，等你答）
   - 结束时 frontier 为空——每个分支都访问过，没有默默假设的东西
   - **产出**：`CONTEXT.md`（领域词汇表）+ `docs/adr/*.md`（难逆转的决策）

2. **没 repo 时用 `grill-me`** —— 同样的访谈，stateless，不留文件
   （打磨计划、设计方案、一段文字，任何没有 repo 承载的东西）

3. **遇到"必须跑起来才知道"的问题** → 不要硬猜，绕行：
   ```
   handoff  →  导出上下文，开 fresh session
   prototype  →  用 throwaway 代码回答问题（logic 分支 / UI 分支）
   handoff  →  把结论带回原线程
   ```

4. **对齐完成 → 接 [04-planning](04-planning.md)（写 spec + 拆 ticket）**

## 需确认

- 一轮问完后**等用户回答再进下一轮**。不要自己假设答案继续往下推。
- 用户确认"我们达成共识了"之前，**不要采取行动**。
- `grill-with-docs` 会写 `CONTEXT.md` 和 ADR——如果用户不想在项目里留文件，提前说明并改用 `grill-me`。

## 常见坑

1. **一轮问太多问题。** 只问 frontier 上的（前置条件已定的），依赖未定答案的问题属于**更晚的**一轮。
2. **问用户你自己能查到的事。** 文件内容、依赖版本、目录结构——这些是你的活。
3. **访谈做成了问卷。** 每个问题要带**推荐答案**，让用户能一句话确认或否掉。
4. **对齐完不留痕迹。** 用 `grill-with-docs` 而不是 `grill-me`，否则下个 session 从零开始。
5. **跳过对齐直接 implement。** 这是整套 skill 存在的主要理由，别绕。

## 边界

- 完全没方向、想法还没成型 → 先走 [01-kickoff](01-kickoff.md)
- 需求已经清楚，只是要写下来 → 直接 [04-planning](04-planning.md) 用 `to-spec`
- 卡住你的东西不在你脑子里而在**别人**脑子里 → 用 `to-questionnaire` 做一份问卷，见 [08-collaboration](08-collaboration.md)
