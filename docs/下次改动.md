```markdown
## 第 0 步：看手上有什么牌
```

## 待做 3 · 「又…又…」多技能编排

**✅ 验收标准（改完必须拿实例演示）**
- 说"**既要重构又要顺手把界面弄好看点**" → 它**列出 串行 / 分工 / 只跑一个 三个选项让你挑**，而不是自己闷头挑一个
- 你选了"串行" → 它**真的先做完重构、再动界面**，并在计划里说明为什么是这个顺序
- 反例（防止过度触发）：只说"帮我改一下界面" → 它**不该**弹三个选项（只有一个需求，没什么可编排的）

**问题**：现在的执行原则只说"一次只让一个流程型 skill 主导"，
但**没说遇到"既要 A 又要 B"该怎么办**。用户说"既要重构又要顺手把界面弄好看点"，
现在的行为是未定义的。

**抄谁**：`Liber1917/skill-router` 的做法 —— 遇到多技能需求，**给三个选项让用户挑**：

| 选项 | 什么时候用 |
|---|---|
| **串行** | 两件事有依赖（先重构完再改界面，不然白改） |
| **分工** | 两件事互不干扰（一边改后端一边改前端） |
| **只跑一个** | 其中一件是主，另一件顺手提一句就够 |

**加在哪**：`SKILL.md` 的「执行原则」段，作为第 1 条的补充。

## 待做 6 · 优先级 + 冲突解决（扩写）

**✅ 验收标准**
- 提一个同时命中 `tdd`（流程）和 `ui-styling`（领域）的需求 → 它**先定测试怎么写、再进界面**，并说明这个顺序的理由
- 提一个只命中领域 skill 的需求 → 它**不硬塞流程 skill**（防止"为了用规则而用规则"）

**现在**：执行原则 1 只说"一次只让一个流程型 skill 主导"。
**缺**：多个 skill 都可能命中时，**谁优先**、**冲突了听谁的**。

**加进去**：
> 多个 skill 同时命中时，**流程型优先**（先定方法，再干活）。
> 例：既命中 `tdd`（流程）又命中 `ui-styling`（领域）→ 先用 tdd 定测试怎么写，再进 ui-styling。

> 同为流程型且都命中 → **更具体（范围更窄）的赢**；一样具体按字母序；互不冲突的可以一起上。

## 待做 7 · 补一个独立的「验证」环节（本次新发现）

**✅ 验收标准**
- 报一个具体现象（如"**点保存按钮没反应**"）→ 修完后它**主动用"点保存按钮"这个原始现象再走一遍**，而不是只说"测试通过了"
- 它必须**明确区分**："单元测试过了" 和 "你报的现象消失了" 是**两件事** —— 前者不算完成

**问题**：`obra/superpowers` 的 14 步链里，**「验证」是独立一步**（头脑风暴 → 计划 → 执行 →
TDD → 系统调试 → **验证** → 审查 → 收尾）。我们的链**缺这一环**：

- `06-debugging.md` 有「根因」「复现」「需确认」，但**没有"改完怎么确认原来那个问题真没了"**
- `10-shipping.md:51` 的「怎么验证」是**交付说明模板里的一栏**（写给读的人看的），
  不是给 agent 执行的步骤

**症状**：典型的「测试过了 ≠ 问题解决了」。改完跑一遍测试绿了就交付，
但用户报的那个现象根本没复测。

**要加的**：`06-debugging.md` 末尾加一步 —— **用用户当初报现象的方式再走一遍**，
并明确"测试通过只是必要条件，不是充分条件"。

## 待做 8 · 补一条「置信度门槛」（本次新发现）

**✅ 验收标准**
- 说一句模糊的（如"帮我看看这个"）→ 它**先问一个能区分阶段的问题**，而不是硬套一个配方
- **反过来也要验**：你说得足够清楚时 → 它**直接给配方，不多问**。门槛高 ≠ 什么都问

**问题**：现在的阶段对照表是**只要沾边就出手**。没写"拿不准时怎么办"。

**抄谁**：
- `pcx-wave/skill-router` —— **只有关键词明显对上才出手，不确定就不吭声**
- `Liber1917/skill-router` —— 置信度阈值 0.85

**要加的**（放在 SKILL.md「1. 定位阶段」里）：
> 拿不准在哪个阶段时 —— **先问，别硬套**。猜错阶段的代价 > 多问一句的代价。
> （和"一次只问一个问题"配合：问那个最能区分两个候选阶段的问题。）

**注意**：门槛高 ≠ 不出手。是"**明显对上才出手**"，不是"要 100% 确定才出手"。

## 调研结论 · 8 个 skill-router 方案（2026-09-16）

荆丝从外网收集了一份速查表（已存档在 `docs/参考/skill-router-8-cheatsheet.md`）。

**结论：一个都不装。**

### 以后的判断规则（重要）

不是"永远不装别人的 skill"，而是按这个顺序判断：

1. **先看自己有没有** → 有就不装（重复造轮子，还多一份维护负担）
2. **缺的优先"抄思路"，不是"抄代码"** —— 别人的 skill 是别人的场景，直接装会捎带：
   多余 hook、强制播报、外部依赖、API key、绑死它自己的目录结构
3. **只有整块能力都缺 + 它零依赖 + 行为可预期** → 才考虑装
4. **抄的时候只抄"规则"** —— 比如待做 3 抄的是「串行 / 分工 / 只跑一个」这个决策框架，
   不是它的实现代码

**为什么定制化更划算**：本项目自己写的那几行规则，是**贴着自己的场景**长的，
改起来只动一个文件；装别人的，出问题要先去读它的源码才知道卡在哪。

## 思考结论 · 后面加 skill 怎么办

**索引不会自动更新**，分三种情况：

| 你怎么加 skill | 索引会自动更新吗 | 怎么办 |
|---|---|---|
| 自己新建 / 改自己的 → 放 `skills/` 再跑 `deploy.py` | ✅ 会（deploy 自动重建） | 正常走 |
| 从 GitHub 装别人的 → 直接放进 `~/.workbuddy-ai/skills/` | ❌ 不会 | 手动跑 `rebuild-index.py` |
| 删掉某个 skill | ❌ 不会（deploy 只增改不删） | 手动删部署目录里的旧副本 |

**待做 1 的自检能兜住第 2 行**（读索引时发现对不上就重建）。
第 3 行是已知限制，见 `AGENTS.md` 第 7 条。

## 思考结论 · 三个位置的关系（**不会自动同步**）

| 位置 | 是什么 |
|---|---|
| 任意工作区（比如聊天时开的） | 对话的地方，临时 |
| `Desktop\skill-lab\` | **源码，唯一源头** |
| `~\.workbuddy-ai\skills\` | 部署目标，WorkBuddy 读这里 |

```
① 工作区  ──✗──▶  ② 项目  ──✗──▶  ③ 部署
                        （要手动跑 deploy.py）
```

**没有任何自动同步。** 所以：

- **改 skill → 改 `Desktop\skill-lab\skills\` 里的**，再 `python scripts/deploy.py`
- 直接改 `~\.workbuddy-ai\skills\` → 项目落后 → 下次 deploy 覆盖掉你的改动
- 改了之后**当前对话不会生效**（skill 在对话开始时加载）→ 要新开对话
